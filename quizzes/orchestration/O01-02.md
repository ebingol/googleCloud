# O01-02 — Microservice boundaries and choosing a starting architecture

5 soru. Her soruda seçilecek cevap sayısı belirtilmiştir.

**Kaynak türü:** Introduction to Microservices PDF.

## 1. Which two properties define microservices in the module?

**Select two.**

- A. Loose coupling
- B. One mandatory central ESB controlling every change
- C. Separate services with limited scope
- D. One inseparable deployment unit for all business domains

## 2. How are orders, products and reviews modeled in the decomposition example?

**Select one.**

- A. Only separate UI screens over unchanged tightly coupled code
- B. A single shared data-access component used directly by all callers
- C. A single service with three names
- D. Separate services, each with its own database

## 3. What do callers typically use to invoke a microservice's operations?

**Select one.**

- A. A shared copy of its in-memory objects
- B. The implementation language's private classes
- C. Direct access to all internal database tables
- D. Its defined API interface

## 4. Which three conditions support starting directly with microservices in the module?

**Select three.**

- A. Requiring all changes to ship as one inseparable release
- B. Understanding the problem domain
- C. Having no idea how to define service boundaries
- D. Planning to grow the team
- E. Needing agile service delivery

## 5. A team does not yet understand its problem domain well. What starting approach does the module allow?

**Select one.**

- A. Build a modular monolith and separate services as understanding improves
- B. Create arbitrary service boundaries immediately and never revise them
- C. Require an enterprise ESB before any code can be written
- D. Avoid modularity because future migration is impossible
